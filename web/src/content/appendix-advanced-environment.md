# Appendix: 上級者環境の実例 — Second Brain を極限まで構築した環境

本 Appendix では、Phase 0-5 のすべてを実装し、長期運用している実環境を紹介する。
各領域の設計と、それが **品質・スピード・自律性・認知負荷** の 4 軸にどう効くかを解説する。

> 以下の表の見方:
> - **品質**: AI の出力品質を高める効果
> - **スピード**: 作業速度・スループットを上げる効果
> - **自律性**: 人間不在でも AI が正しく動く効果
> - **認知負荷**: 人間が考える量・判断する量を減らす効果
>
> ◎ = 極めて高い効果 / ○ = 効果あり / △ = 間接的な効果

## A. アーキテクチャ設計

### 何が優れているか

**設定の階層構造と正規化原則**

```
CLAUDE.md（3行以内）     ← 横断的な基本ルール。肥大化させない
  ↓
rules/（5ファイル）       ← ファイル種別・横断的な制約（常時適用）
  ↓
skills/（6スキル）        ← 行動パターン（トリガー起動）
  ↓
memory/（プロジェクト別） ← 蓄積された知見（自動読み込み）
  ↓
framework.md              ← ユーザーの原理原則（10の根本思想）
```

**設計原則:**
- **思想と行動の分離**: rules = 制約（常時適用）、skills = アクション（明示トリガー）
- **同じ知識を 2 箇所に書かない**: 蒸留ロジックの正規化先は wrapup/SKILL.md が権威ソース
- **CLAUDE.md は 3 行以内**: コンテキストウィンドウの浪費を防ぐ。詳細は rules/skills に分散

| 品質 | スピード | 自律性 | 認知負荷 |
|------|---------|--------|---------|
| ◎ | ○ | ◎ | ◎ |

**なぜ効くか:**
- AI は常に必要十分な文脈だけを読み込む（コンテキスト汚染の防止 → 品質）
- 情報の重複がないため、更新は 1 箇所だけで済む（メンテナンスの認知負荷削減）
- rules が常時適用されるため、人間が毎回指示しなくても AI が制約を守る（自律性）

## B. プリセット: Rules

### B-1. 自律駆動ポリシー（autonomous-operation.md）

```
基本方針:
- ユーザー離席中でも作業を継続する
- 承認プロンプトは最小限に抑える
- 判断に迷う場合は実行側に倒す

課金操作の制約:
- 1回 $10 未満 → 自律実行可
- 1回 $10 以上 → 承認を得る
- 日次累計 $50 以上 → 承認を得る

機密ファイルの保護:
- .env, rules/, CLAUDE.md → 直接編集せず .proposed ファイルで提案
```

| 品質 | スピード | 自律性 | 認知負荷 |
|------|---------|--------|---------|
| ○ | ◎ | ◎ | ◎ |

**なぜ効くか:**
- 「迷ったら実行側に倒す」ルールにより、AI が承認待ちで停止しない（スピード）
- 課金上限の定量基準により、AI が自分で判断できる（自律性 + 認知負荷削減）
- .proposed フローにより、機密ファイルは人間が最終確認（品質担保）

### B-2. 問題解決フレームワーク（problem-solving-framework.md）

```
4原則:
1. 問題解決 = 行動を決めること（行動を伴わない問いは無意味）
2. 論点には必ず「べき」を含める（「Aは魅力的か」→「Aを採用すべきか」）
3. 正しく間違える（小さく・検証可能な形で間違え、致命的失敗は回避）
4. 曖昧性を排除（「良い」「早い」を数値・基準に変換）

6ステップ:
論点定義 → 論点分解 → 仮説構築 → トレードオフ評価 → 解の定義 → ネクストアクション
```

| 品質 | スピード | 自律性 | 認知負荷 |
|------|---------|--------|---------|
| ◎ | ○ | ◎ | ○ |

**なぜ効くか:**
- AI が曖昧な問いを自律的に構造化し、定量的な仮説を出せる（品質 + 自律性）
- 「5分以上 1 つの論点を考えない」ルールにより、AI が延々と考え続けることを防止（スピード）
- ユーザーの思考パターンを AI が内面化するため、AI の出力が「自分の分身」に近づく

### B-3. サブエージェントのモデル選択ルール（subagent-model-selection.md）

```
Explore（ファイル探索）      → haiku（軽量・安価）
general-purpose（リサーチ）   → sonnet（十分な品質）
Plan（設計立案）              → sonnet（最終判断はユーザー）
claude-code-guide（使い方）  → haiku（ドキュメント参照のみ）
例外: 複雑な設計 → opus
```

| 品質 | スピード | 自律性 | 認知負荷 |
|------|---------|--------|---------|
| ○ | ◎ | ◎ | ◎ |

**なぜ効くか:**
- タスクの知的要求度に応じてモデルを自動選択（コスト最適化 + スピード向上）
- AI が自分でモデルを選ぶため、人間が毎回指定する必要がない（認知負荷削減）
- 不必要に高性能なモデルを使わないため、レスポンスが速い（スピード）

### B-4. Git セーフティネット（git-safety.md）

```
- ~/workspace/projects/ 配下のみ適用
- 自動コミット: auto: <ファイル名> 形式
- Bash 実行前にスナップショットコミット
- セッション終了時に auto: コミットを squash
- .git サイズ 100MB 超で通知
```

| 品質 | スピード | 自律性 | 認知負荷 |
|------|---------|--------|---------|
| △ | ○ | ◎ | ◎ |

**なぜ効くか:**
- ファイル変更が即座にコミットされるため、AI の誤操作からいつでも復旧可能（自律性の安全担保）
- squash 運用により、最終的なコミット履歴はクリーンに保たれる（品質）
- 人間が「コミットしたかな？」と心配する必要がない（認知負荷削減）

## C. プリセット: Skills

### C-1. セッション開始（startup）

```
実行フロー:
1. 直近3日のタスクアーカイブ → 未完了タスク抽出
2. Git 状態（uncommitted/unpushed）確認

| 品質 | スピード | 自律性 | 認知負荷 |
|------|---------|--------|---------|
| ○ | ◎ | ◎ | ◎ |

- 持ち越しタスクの漏れがなくなる（品質）

### C-2. セッション終了（wrapup）

```
実行フロー:
1. 残論点確認（完了/未解決/申し送り）
2. 蒸留判定（2つのレンズ）:
   - レンズA: 技術知見 → CLAUDE.md/rules/skills に配置
   - レンズB: 原理原則 → framework.md に配置
3. 統合レポート出力
4. タスクアーカイブ → ~/workspace/archive/tasks/YYYYMM/
5. 蒸留の書き出し（ユーザー承認後）
```

| 品質 | スピード | 自律性 | 認知負荷 |
|------|---------|--------|---------|
| ◎ | ○ | ○ | ◎ |

**なぜ効くか:**
- セッションの学びが自動的に永続化される（思考の連続性 = Second Brain の核心）
- 蒸留先が明確（CLAUDE.md / rules / skills / framework.md）なので、情報が散乱しない（品質）
- ユーザーは「何を覚えておくべきか」を考えなくて良い（認知負荷削減）

### C-3. startup + wrapup の循環

```
wrapup（セッション終了）
  ↓ 蒸留 → preset に反映
  ↓ アーカイブ → tasks/ に記録
startup（次セッション開始）
  ↓ アーカイブ読み込み → 未完了タスク検出
  ↓ preset 読み込み → 前回の学びが反映済み
  ↓ 即座に作業開始
```

**この循環が回り続けることで、AI は使うほど賢くなる。** これが「ツール」と「Second Brain」の決定的な違い。

## E. プリセット: Data

### E-1. framework.md — ユーザーの原理原則

10の根本思想が明文化されている:

```
1. 最小限主義      — 必要最小限だけ配置。二重記録を避ける
2. 永続化の閾値    — 繰り返し参照するパターンのみ記録

## F. 安全装置

### F-1. AI レビュアー（reviewer.py）

```
全ツール実行前に Codex CLI（外部 AI）がリスク判定:

1. ツール分類（即時判定）:
   readonly（Read, Glob 等） → 即座に許可（0ms）
   always_allow（TaskCreate 等） → 即座に許可

2. リスク分析（パターンマッチ）:
   highly_dangerous（rm -rf / 等） → フラグ立て
   sensitive_file（.env, CLAUDE.md 等） → フラグ立て
   costly_operation（gcloud deploy 等） → フラグ立て

3. Codex CLI に判定委譲（2-7秒）:
   → APPROVE or DENY を応答

4. フォールバック（Codex 応答なし時）:
   dangerous/sensitive/costly → 自動 DENY
   その他 → 自動 ALLOW
```

**ログ記録（全決定を監査可能）:**
```
[時刻] SKIP | Read | {"file_path": "..."} | reason=readonly_tool | 0ms
[時刻] APPROVE | Bash | cmd=npm test | reason=codex: APPROVE | 4205ms
[時刻] DENY | Bash | cmd=rm -rf ... | reason=codex: DENY | 5981ms
```

| 品質 | スピード | 自律性 | 認知負荷 |
|------|---------|--------|---------|
| ◎ | ○ | ◎ | ◎ |

**なぜ効くか:**
- 人間の代わりに AI が全操作を監視（認知負荷の劇的削減）
- readonly ツールは 0ms で通過するためボトルネックにならない（スピード）
- Codex CLI 障害時も「危険な操作は自動 DENY」のフォールバックで安全確保（自律性）
- Claude (Anthropic) の操作を Codex (OpenAI) がレビューする**異なる AI による相互監視**（品質）

### F-2. Git 自動コミット（auto-commit.sh）

```
PostToolUse（Edit/Write）→ 変更後に即座にコミット
PreToolUse（Bash）       → コマンド実行前にスナップショット

コミットメッセージ:
  auto: <filename>                    ← 単一ファイル
  auto: <file> (+N files)             ← 複数ファイル
  auto(pre-bash): snapshot before command ← Bash 実行前

適用除外: ~/（ホーム直下）、/tmp/、~/.claude/
```

| 品質 | スピード | 自律性 | 認知負荷 |
|------|---------|--------|---------|
| △ | ◎ | ◎ | ◎ |

**なぜ効くか:**
- AI が破壊的な変更をしても `git reset HEAD~1` で即座に復旧可能（自律性の安全ネット）
- 人間が「コミットし忘れた」リスクがゼロ（認知負荷削減）
- `--no-verify` で reviewer.py との循環を回避（スピード担保）

### F-3. 3 層防御アーキテクチャ

```
┌─ Layer 1: permissions（settings.json）─────────┐
│  ハードリミット。物理的にブロック                  │
│  allow: Read, Write, Edit, Bash(npm test*) 等    │
│  deny: Bash(rm -rf *), Bash(git push --force*)   │
└─────────────┬────────────────────────────────────┘
              │
┌─────────────▼────────────────────────────────────┐
│  Layer 2: Hooks（reviewer.py）                    │
│  AI による動的リスク判定。Codex CLI に委譲          │
│  → Codex 障害時は安全側にフォールバック             │
└─────────────┬────────────────────────────────────┘
              │
┌─────────────▼────────────────────────────────────┐
│  Layer 3: Rules（autonomous-operation.md）        │
│  AI 自身の判断基準。課金上限、機密保護              │
│  → AI が「やるべきでない」と自己判断                │
└──────────────────────────────────────────────────┘
```

**3 層が独立して機能する:**
- Layer 1 が突破されても Layer 2 が止める
- Layer 2（Codex）が落ちても Layer 3（AI の自己制御）が止める
- Layer 3 も突破された場合は Layer 1 の deny リストが最終防壁

## G. 外部 AI 統合（Codex CLI）

### なぜ外部 AI を統合するのか

Claude Code（Anthropic）だけでは**自分の行動を客観的にレビューできない**。
Codex CLI（OpenAI の gpt-5.3-codex）を統合することで、**異なる AI が相互監視・議論する**構造を実現。

### 3 つの統合パターン

| パターン | 用途 | 呼び出し元 |
|---------|------|-----------|
| reviewer.py | 全ツール実行の安全レビュー | PreToolUse フック（自動） |
| github-workflow | PR のセルフレビュー（最大 3 ラウンド） | github-workflow スキル |
| codex-discuss | 技術議論の深掘り（最大 5 ラウンド） | codex-discuss スキル |

| 品質 | スピード | 自律性 | 認知負荷 |
|------|---------|--------|---------|
| ◎ | ○ | ◎ | ◎ |

**なぜ効くか:**
- framework.md の「異質な視点の衝突」原則を AI 同士で実現（品質の根本的向上）
- レビューが自動的に行われるため、人間がコードを逐一チェックする負荷が減る（認知負荷）
- 認証は 1Password 統合（`op read` で動的取得）。環境変数にキーを埋め込まない（セキュリティ）

## H. セッションライフサイクル

### 全体フロー

```
[セッション開始]
  │
  ├─ /startup 実行
  │   ├─ 前回のアーカイブ読み込み → 未完了タスク検出
  │   ├─ Git 状態確認 → uncommitted/unpushed の把握
  │   ├─ .proposed ファイル検索 → 保留中の提案確認
  │   └─ 即座に作業開始（ユーザー確認不要）
  │
  ├─ [作業中]
  │   ├─ reviewer.py: 全ツール実行を AI レビュー
  │   ├─ auto-commit.sh: ファイル変更を即座にコミット
  │   ├─ rules: 問題解決フレームワーク・自律駆動ポリシーが常時適用
  │   ├─ memory: 過去の判断・知見が自動参照
  │   └─ skills: 定型業務（research, github-workflow 等）をスキルで実行
  │
  ├─ /wrapup 実行
  │   ├─ 残論点確認
  │   ├─ 蒸留（技術知見 → rules/skills、原理原則 → framework.md）
  │   ├─ タスクアーカイブ → ~/workspace/archive/tasks/YYYYMM/
  │   └─ auto: コミットの squash
  │
  └─ [次のセッションで /startup → 前回の続きから再開]
```

| 品質 | スピード | 自律性 | 認知負荷 |
|------|---------|--------|---------|
| ◎ | ◎ | ◎ | ◎ |

**なぜ効くか:**
- セッション間の文脈断絶がゼロ。AI は前回の続きから再開する（思考の連続性）
- 蒸留サイクルにより、使い続けるほど preset が厚くなり精度が上がる（品質の継続的向上）
- 人間は「前回何をやっていたか」を思い出す必要がない（認知負荷の劇的削減）
- AI がタスクの優先度を判断し、確認なしで作業を開始する（自律性 + スピード）
