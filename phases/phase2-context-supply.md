# Phase 2: Context Supply（文脈供給）

## 到達状態

> AI が「自分の仕事の進め方」を理解している。
> 毎回背景から説明しなくても、自分好みのアウトプットが出る。

## なぜ文脈供給が重要か

Phase 1 では AI に毎回「何をしてほしいか」を説明していた。しかし、実際の業務には以下のような「暗黙の前提」がある:

- 自分の役割と責任範囲
- プロジェクトの背景と現状
- アウトプットの形式（社内報告書のフォーマット等）
- 意思決定の基準（コスト重視か品質重視か等）
- 使用する用語・表現のルール
- 関係者のステークホルダーマップ

これらを**毎回プロンプトに書く**のは非効率であり、書き忘れると AI の出力がズレる。
**preset（事前設定）として永続化する**ことで、AI が常に「自分の頭の延長」として機能する。

> **これが「ツール」と「Second Brain」の分水嶺。**
> preset のない AI はただの汎用ツール。
> 自分の文脈が注入された AI は Second Brain になる。

## 2-1. CLAUDE.md — 自分の「頭の中」を AI に渡す

### CLAUDE.md とは

CLAUDE.md は Claude Code が**セッション開始時に自動的に読み込む**ファイル。
ここに書いた情報は、毎回のプロンプトに含めなくても AI が常に知っている状態になる。

### 配置場所と使い分け

> **ファイルパスの読み方**: `~` は自分のホームフォルダ（Mac: `/Users/あなたの名前`、Windows: `C:\Users\あなたの名前`）を意味します。`/` はフォルダの階層区切りです。

```
~/.claude/CLAUDE.md              ← グローバル（すべての作業で共通）
~/project-x/CLAUDE.md            ← プロジェクト固有（このプロジェクトだけ）
~/project-x/docs/CLAUDE.md       ← サブディレクトリ固有（この領域だけ）
```

すべてのレベルが読み込まれ、深い階層ほど優先される。

### グローバル CLAUDE.md に書くべきこと

**自分自身の情報（全プロジェクト共通）:**

```markdown
# 基本方針
- 日本語で回答する
- 文体は「です・ます」調

# 自分の役割
- 事業開発部マネージャー
- 担当領域: 新規事業の企画・推進
- レポートライン: 事業本部長

# アウトプットの基本形式
- 報告書は「結論→根拠→詳細」の順序で構成する
- 箇条書きは 3-5 項目を基本とする
- 数値には必ず比較対象を添える（前年比、目標比等）

# 意思決定の基準
- ROI を最優先で評価する
- リスクは「発生確率 × 影響度」で定量化する
- 不確実性が高い場合は小さく試してから判断する
```

### プロジェクト固有の CLAUDE.md に書くべきこと

```markdown
# プロジェクト概要
新規 SaaS プロダクト「XXX」の企画・開発プロジェクト。
ターゲット: 中小企業の経理部門。課題: 請求書処理の工数削減。

# 現在のフェーズ
PMF 検証中（2026年1月〜）。パイロット顧客 5 社で検証中。

# 主要ステークホルダー
- PO: 田中（意思決定者）
- Tech Lead: 佐藤（技術判断）
- 営業: 鈴木（顧客接点）

# KPI
- パイロット顧客の継続率: 80% 以上
- 請求書処理時間: 50% 削減
- NPS: +30 以上

# 用語集
- FP: フルフィルメントパートナー（請求書発行代行業者）
- INV: インボイス（適格請求書）

# よく使うツール・操作
- プロジェクト管理: Notion の「XXX プロジェクト」ページ
- データ共有: Google Drive の「XXX」フォルダ
- 開発チーム向け: npm run dev（サーバー起動）、npm test（テスト実行）
```

### CLAUDE.md に書くべきでないこと

| 書くべきでない | 代わりにどこに書くか | 理由 |
|---------------|-------------------|------|
| 一般常識・業界の基礎知識 | （記述不要） | AI はすでに知っている |
| 巨大な資料の全文 | `@file` で都度参照 | コンテキストウィンドウを浪費する |
| 頻繁に変わるステータス情報 | Memory（Phase 3） | CLAUDE.md は安定した情報のみ |
| 機密情報（パスワード等） | シークレット管理ツール | セキュリティリスク |

### 判断基準: 「これを CLAUDE.md に書くべきか？」

```
この情報がないと AI はズレたアウトプットを出すか？
  → Yes、かつ月単位で安定している → CLAUDE.md に書く
  → Yes、かつ頻繁に変わる         → Memory に書く（Phase 3）
  → No                           → 書かない
```

## 2-2. Claude Code Rules — アウトプット形式と制約の設定

### Rules の配置

Claude Code では `~/.claude/rules/` に Rules ファイルを配置できる。

```
~/.claude/
└── rules/
    ├── report.md              # 報告書・レポートの規約
    ├── email.md               # メール作成の規約
    └── analysis.md            # 分析・調査の規約
```

プロジェクト固有の Rules は `.claude/rules/` に配置する:

```
~/project-x/
└── .claude/
    └── rules/
        └── coding-style.md    # プロジェクト固有のルール
```

### 効果的な Rule の書き方

**原則: 具体的・実行可能・検証可能**

```markdown
# 悪い例
- わかりやすく書く
- 適切な長さにする

# 良い例
- 1文は 60 文字以内にする。超える場合は分割する
- 要約は 3 つの箇条書きで構成する
- 数値は「XX（前年比 +YY%）」の形式で記述する
```

### CLAUDE.md と Rules の使い分け

```
┌──────────────────────────────────────────┐
│  業務知識・判断基準・プロジェクト文脈      │
│  → CLAUDE.md に記述                      │
│  （AI が「何を知っているべきか」）         │
└──────────────────────────────────────────┘

┌──────────────────────────────────────────┐
│  アウトプットの形式・スタイル規約          │
│  → rules/ に記述                         │
│  （AI が「どう書くべきか」）               │
└──────────────────────────────────────────┘
```

**CLAUDE.md = 知識**、**Rules = 表現のルール** と覚える。

## 2-3. 実践: 文脈供給の設定

### 演習 1: グローバル CLAUDE.md を作成する

1. `~/.claude/CLAUDE.md` を作成する
2. 自分の役割、アウトプット形式、意思決定基準を記述する
3. Claude Code を起動し「来週の部門ミーティングのアジェンダを作って」とリクエスト
4. CLAUDE.md の情報が反映されたアウトプットが出ることを確認

### 演習 2: プロジェクト固有の CLAUDE.md を作成する

1. 担当プロジェクトのディレクトリに `CLAUDE.md` を作成
2. プロジェクト概要、KPI、ステークホルダー、用語集を記述
3. Claude Code で「プロジェクトの進捗報告書のドラフトを作って」とリクエスト
4. プロジェクト固有の文脈が反映されていることを確認

### 演習 3: 文脈供給の効果を比較する

1. CLAUDE.md なしで「月次レポートを作って」とリクエスト（結果を保存）
2. CLAUDE.md ありで同じリクエスト（結果を保存）
3. 出力の違いを比較し、文脈供給の効果を実感する
