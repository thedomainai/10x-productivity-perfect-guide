# Phase 5: Autonomous（自律駆動）

## 到達状態

> AI が先回りして情報を整理し、人間は判断と意思決定だけに集中できる。
> 適切な安全装置が設計されており、リスクを管理しながら AI に権限を委譲している。

## Phase 5 の位置づけ

Phase 0-4 で精度の基盤（蛇口）が整った。Phase 5 では**量の最大化（ひねる量）**に取り組む。

```
推論の量 = 速度 × 持続時間 × 並列度

速度      → 承認プロンプトの排除、自動実行
持続時間  → 人間不在でも作業を継続
並列度    → 複数タスクの同時実行
```

ここまでの Phase で「AI に何を知らせるか」「AI に何をさせるか」を設計した。
Phase 5 では「AI をどれだけ速く・長く・多く動かすか」を設計する。

## 5-1. 速度の向上 — 承認プロンプトの最適化

### デフォルト動作

Claude Code はファイル書き込みやコマンド実行の前に承認を求める。これは安全だが、人間が常に画面を見ている必要があり、**推論速度が制限される**。

### 承認ポリシーの設計

リスクに応じて承認の粒度を設計する:

```
リスクレベル    例                          承認
────────────────────────────────────────────────
低リスク        ファイル読み取り            自動許可
              ファイル作成・編集
              Web 検索

中リスク        コマンド実行（テスト等）    自動許可（条件付き）
              外部 API 呼び出し

高リスク        外部サービスへの書き込み    手動承認
              メール・メッセージ送信
              課金が発生する操作

禁止            機密ファイルの変更          ブロック
              個人情報の外部送信
```

### 設定方法

```json
// ~/.claude/settings.json
{
  "permissions": {
    "allow": [
      "Read",
      "Glob",
      "Grep",
      "Write",
      "Edit",
      "Bash(npm test*)",
      "Bash(npm run build*)"
    ],
    "deny": [
      "Bash(rm -rf *)"
    ]
  }
}
```

## 5-2. 安全装置の設計

### なぜ安全装置が必要か

自律駆動の恩恵は「人間が介入しなくても AI が動く」こと。
しかし、**致命的な失敗（取り消せない操作）を防ぐガードレール**がなければ、委譲は危険になる。

### 安全装置の 3 層構造

```
┌─────────────────────────────────────────┐
│ Layer 1: 権限設定（settings.json）       │
│ → 許可/拒否のリスト                      │
│ → 「何ができるか」のハードリミット        │
└──────────────────┬──────────────────────┘
                   │
┌──────────────────▼──────────────────────┐
│ Layer 2: Hooks（PreToolUse）             │
│ → 実行前のカスタムチェック                │
│ → 「本当に実行して良いか」のソフトチェック │
└──────────────────┬──────────────────────┘
                   │
┌──────────────────▼──────────────────────┐
│ Layer 3: Rules                           │
│ → AI 自身の判断基準を文章で定義           │
│ → 「どう判断すべきか」の方針              │
└─────────────────────────────────────────┘
```

### Layer 1: 権限設定

前セクション（5-1）で設定済み。

### Layer 2: Hooks による安全チェック

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "command": "python3 ~/.claude-tool-reviewer/reviewer.py"
      }
    ]
  }
}
```

Hooks で実現できるチェックの例:

| チェック | 内容 |
|---------|------|
| 破壊的操作の検知 | ファイル削除、DB 操作等をブロック |
| 機密ファイルの保護 | `.env`、認証情報ファイルへの書き込みをブロック |
| 課金操作の制限 | デプロイ等の課金操作を検知して承認要求 |
| 外部送信の監視 | 機密情報を含むリクエストをブロック |

### Layer 3: Rules による AI の自己制御

```markdown
# autonomous-operation.md

## 基本方針
- 判断に迷う場合は実行側に倒す
- ただし、取り消せない操作は必ず確認する

## 課金操作の制約
- 1回 $10 未満: 自律実行可
- 1回 $10 以上: 承認を得る

## 機密ファイルの保護
以下を更新する場合は提案ファイル（.proposed）を作成し、直接編集しない:
- .env, .env.*
- 認証情報ファイル
```

## 5-3. 持続時間の向上 — バックグラウンド実行

人間が離席しても AI が作業を継続できるようにする。

```bash
# バックグラウンドで Claude Code を実行
claude -p "来週のプレゼン用に競合5社の最新動向を調査してレポートにまとめて" &

# 非対話モードで実行（特定のツールのみ許可）
claude -p "docs/ フォルダ内の全ドキュメントの要約一覧を作って" \
  --allowedTools "Read,Glob,Grep,Write"
```

**ポイント**: 朝一番に Claude Code にリサーチを投げておき、自分はミーティングに出る。戻ってきたらレポートが完成している。

## 5-4. 並列度の向上 — 複数タスクの同時実行

Phase 4 では Claude Code を業務に組み込むワークフローパターンを学んだ。
Phase 5 では**複数の Claude Code インスタンスを並列実行**する。

### パターン 1: 独立タスクの並列実行

```bash
# タスク 1: 競合分析
claude -p "競合A社の最新プレスリリースを調査してまとめて" &

# タスク 2: 市場データ整理
claude -p "market-data.csv を分析して四半期トレンドをまとめて" &

# 人間: 別の仕事に集中
wait
```

### パターン 2: 多角的調査の並列実行

同じテーマを異なる角度から同時に調査させる:

```bash
# 市場の観点
claude -p "SaaS市場の2026年トレンドを調査して" &

# 技術の観点
claude -p "AI/LLM技術の最新動向を調査して" &

# 競合の観点
claude -p "主要競合3社の直近の動きを調査して" &

wait
# 3つのレポートを統合して経営会議資料にする
```

### パターン 3: ドラフトの並列生成

```bash
# 2つのアプローチで提案書を作らせ、良い方を選ぶ
claude -p "コスト削減の観点でA案の提案書を作って" &
claude -p "売上拡大の観点でB案の提案書を作って" &
wait
```

### 並列度の設計指針

| 並列数 | 適する場面 | 注意点 |
|-------|-----------|--------|
| 1（直列） | 結果が次のステップに必要な場合 | 順序保証 |
| 2-3 | 独立した調査・文書作成 | API コストを意識 |
| 4+ | 大量の小タスク | レート制限に注意 |

## 5-5. 継続的な改善サイクル

### AI の出力品質をモニタリングする

自律駆動では人間の介入が減るため、**出力品質のモニタリング**が重要。

```
1. AI に作業させる
2. 出力を確認する
3. 問題があれば原因を分析する
4. preset（Rules / CLAUDE.md / Skills / Memory）を改善する
5. 1 に戻る
```

### 典型的な改善パターン

| 問題 | 原因 | 改善策 |
|------|------|--------|
| 出力のトーンが合わない | Rules の記述が不足 | 文体・トーンのルールを追加 |
| 同じ間違いを繰り返す | Memory に記録がない | Memory にパターンを追加 |
| 特定の業務で止まる | Skills が未定義 | 手順を Skill として定義 |
| 不要な承認が頻繁に出る | 権限設定が狭い | permissions を調整 |
| 知るべき情報を知らない | CLAUDE.md が不足 | 文脈情報を追加 |

### Second Brain の成熟度

```
Phase 2 完了時:  AI は「自分の仕事」を知っている
Phase 3 完了時:  AI は「定型業務」を自動化できる
Phase 4 完了時:  AI を「業務の各場面」で使い分けられる
Phase 5 初期:    AI が「先回りして」動き始める
Phase 5 成熟:    AI が「自分の分身」として自律的に機能する
```

成熟度は preset の厚み（Rules + Skills + Memory の蓄積量）に比例する。
使い続けるほど AI は自分の仕事を理解し、Second Brain としての精度が上がる。

## 5-6. 実践: 自律駆動の構築

### 演習 1: 承認ポリシーを設計する

1. 自分の業務で AI に許可する操作を洗い出す
2. リスクレベルごとに分類する
3. `settings.json` に permissions を設定する
4. 実際に動作させて、適切にブロック/許可されることを確認

### 演習 2: バックグラウンド実行を試す

1. 明日の朝、出社時に Claude Code にリサーチタスクを投げる
2. ミーティングに出て戻ってくる
3. 完成したレポートを確認し、品質を評価する

### 演習 3: 改善サイクルを 1 回回す

1. AI にタスクを実行させる
2. 出力を評価する（品質、正確さ、自分の好みとの一致度）
3. ズレがあれば原因を特定する
4. preset（Rules / CLAUDE.md / Skills / Memory）を改善する
5. 同じタスクを再実行し、改善を確認する

## ガイド全体の完了

Phase 0-5 をすべて完了すると、以下の状態に到達している:

```
Phase 0  Cursor と Claude Code が動作する環境がある
Phase 1  AI に調べさせ、書かせ、整理させることができる
Phase 2  preset により AI が自分の業務を理解している
Phase 3  Skills/MCP/Memory で AI の能力と記憶が拡張されている
Phase 4  業務タスクごとに最適な AI 活用パターンが確立されている
Phase 5  安全装置付きで AI が自律的に動き、改善サイクルが回っている
```

**Second Brain が機能している状態:**

> 自分の頭で「調べる」「整理する」「下書きする」をやめている。
> AI がそれらを担い、自分は「判断する」「決める」「人と話す」に集中している。
> 使い続けるほど preset が蓄積し、AI は自分の仕事をより深く理解していく。
